# Decisions

The decisions that still shape the work, grouped by topic. Code cites them as `D-n`; a number is never reused. Each line says what was decided and, only where it still guides work, why. Details that only describe how something is built live in the code. Trimmed on 2026-11-19 (owner): numbers no longer cited and no longer guiding are in git history only. Audit after each milestone (RULES.md).

## Product and stack

- **D-1, D-2, D-4** A desktop app, since it drives CLIs on the user's machine. The core is its own local process; Electron is a thin shell.
- **D-3, D-12, D-19** TypeScript on Node 24: pnpm, Zod, `node:sqlite`, Electron, React, Vite, Zustand, Biome, Vitest. No build step in development; only the installer is built.
- **D-7** Open source. Free and low-cost models are first class.
- **D-8, D-9, D-11** A command center across harnesses; a harness's own sub-agents show as nested activity. Task agnostic, with connectors as plugins.
- **D-29** No per-agent budgets or dollar tracking; each provider's own limit is the truth.
- **D-115** No Office Town cloud: "cloud" means an always-on machine the user owns, running the same core (M14), with no relay of ours. Order: M10.5 macOS, M11 Unattended runs, M12 Automations, then M15 Ready-made teams (owner, 2026-11-24: it cuts a new user's friction directly), then M13 Remote control and M14 Always-on host once real users ask for them. Numbers stay. Swarms are a scale mode of departments and the chief, capped in window share (D-29 stays). Computer use: a browser connector now; desktop control only in a future sandbox environment, never on the real desktop while the user is away.

## Harnesses

- **D-5, D-13, D-20** One contract, one adapter per wire format. Adapters only translate, do no I/O, and pass the same conformance tests against recordings of the real CLI.
- **D-6** Run the unmodified vendor binary through its official headless mode only, and never touch its credentials. No Google CLIs: their terms risk the user's account.
- **D-14, D-21, D-22** Where a harness runs (native, WSL) is an `Environment`, apart from which harness it is. The agent's own text is never rewritten.
- **D-26, D-28** Models and efforts come from a catalog query. A session resumes by the harness's own id, only in its original environment and folder.
- **D-41** Our tool server is attached and the CLI isolated with its own flags (Claude: `--mcp-config`, `--setting-sources ""`; never `--bare`, which breaks the subscription login). A WSL agent reaches the core through a stdio bridge; the token never goes on a command line.
- **D-76** Harnesses: Claude Code, OpenCode, Codex, Muse, Copilot and Cursor. Adapters declare sign-in, version, install and account folder, so the UI never names a harness. A new harness must not break the others; the app never installs a CLI unasked.
- **D-77, D-83** A message reaches an agent during its turn on every harness, at a tool end, never mid-tool. Conformance checks this on every harness.
- **D-134** Each adapter says how many user messages it holds that the CLI has not taken (`waiting()`); the session reports a change as `message.waiting` during a turn. The trace marks those messages as waiting, and a count left when a session ends names the ones it never read, which its next conversation gets first. Codex and Muse count a steer as taken once the CLI accepts it.
- **D-97, D-98** OpenCode 1 and 2 under one harness, the installed version picking the adapter; 2.x side commands run `--standalone` so the app never touches the user's background service. What 2 adds (steering, sub-agent steps, questions, Code Mode for shared apps only) runs only on 2.
- **D-99** Sub-agents: adapters declare whether steps are shared and whether the CLI wakes the agent itself; otherwise the core sends a short notice once the last sub-agent ends, so the reply is a turn of its own.
- **D-92** One-off CLI queries run two at a time; sessions never wait. Why: each process start blocks the core's thread on Windows.
- **D-117** On a Mac the core reads the login shell's environment once at start (and on Check again), so CLIs installed for Terminal are found. Claude's usage on a Mac is read from its Keychain entry: read only, kept in memory for that one read, never logged or stored, and only on the user's own Refresh on Usage, since macOS may ask before each read (Claude reads it through `/usr/bin/security`, and its token refresh resets the user's answer).

## Core: store, API, live state

- **D-15, D-30** Every event goes to one local SQLite file behind a synchronous store; state and replay are read from it. One core per data folder. Every index serves a named query; no full scans, no `OFFSET`. Migrations are never edited once merged, the file is copied first, and a newer file is refused.
- **D-31** Store, then publish. A shutdown records sessions as interrupted, so "stopped" means someone stopped it. If the store fails, the agent stops: work that cannot be recorded cannot be traced.
- **D-121** Every start no person typed goes through one admission queue, stored before anything starts: the department free, the chief's one goal (D-49), the account below 95% (D-72), at most two unattended starts at a time, spaced (D-92). A person's own start shares the check, so a busy department reads the same everywhere, and still answers at once. At most 100 entries wait, each at most 12 hours, and every wait and skip says why in plain words. In M11 only Resume all and Choose add entries; M12 adds automations.
- **D-17, D-32, D-36** Commands are HTTP; events flow on one SSE stream resuming from `Last-Event-ID`. `127.0.0.1` only, a per-launch token that never reaches a page showing agent text. A preload is plain JS.
- **D-50** Every change to a record is published whole after its write. Task state is decided only in `team/task-state.ts`.
- **D-91** One status rule shared by core and app (`contract/task-status.ts`); the core searches and counts every task.
- **D-93** Provider status is a background job per provider; reads answer at once. Change only what measurements show is slow.

## Shell and packaging

- **D-34** Closing the window keeps agents running in the tray by default (the user can choose Quit, D-111); quitting with agents running asks first and records them as interrupted. The core runs on Electron's own Node and stops when its stdin closes. Why stdin: Windows cannot send a child SIGTERM.
- **D-75** A per-user Windows installer and a Linux AppImage, updated by electron-updater. Every merge publishes a beta only the owner follows; a stable release only when the owner asks, never run by the agent. Bump the version after each release. Updates install on quit or Restart to update, never under a running agent. Dev runs as "Office Town Dev" on its own data folder. Never a one-line PowerShell installer from a hidden process.
- **D-89** The shell adds the usual text menu; app objects get their own menus that only repeat existing actions. Every Stop asks first.
- **D-135** No CI until the public release: `pnpm check` before each PR is the check, and betas build on every merge without waiting. Mac CI and the Mac smoke job hung or failed and held back Windows and Linux betas, so the Mac goes unchecked until then; it still gets a beta, built apart so a Mac failure never holds back the others. Bring CI back, the Mac first, before the public release.
- **D-116** macOS 13 or later on Apple silicon, from the same code; no Intel build unless the owner asks. A .dmg and .zip, ad-hoc signed betas that tell the user an update is ready and link to the download, until an Apple Developer ID is bought before the public release. Mac builds are beta only. Every module from M11 on works on Windows, Linux and macOS. Mac CI paused by D-135.
- **D-123** While agents work, the shell holds `powerSaveBlocker` "prevent-app-suspension" (never the display), asking the core's `GET /keep-awake` every minute and on window events, on battery too. Settings > Desktop "Keep the computer awake while agents work" turns it off; on by default. The app never promises to wake the computer.

## Human in the loop

- **D-10, D-25, D-33** One queue, Needs you, for permission requests and questions.
- **D-40, D-57** Permission levels: Manual and Auto, plus No safety checks behind a warning. Outward actions (push, PR, publish) only under Auto. New work starts at the Settings default, Auto unless the user picks Manual (D-111). Every team proposal and plan waits for the user at every level. Needs you groups by task; Approve all covers approvals only. "Always allow this" rules are parked; the owner wants them later.
- **D-24, D-45** Agents run in the harness's ask mode; one core policy answers each request, and anything it cannot read goes to the user.
- **D-51, D-64** In a read-only folder only reads go through, at every level. The core refuses an answer it did not offer.
- **D-82** A task shows its level once, in a chip that saves on the department or solo agent and applies at the next request.
- **D-71** An agent cutting off another needs the user's approval.
- **D-78** A lead that would change direction asks first with `propose_change`, at every level.
- **D-118** Automations start at the Settings default level; event-triggered ones never use No safety checks. `propose_schedule` always waits for the user. An unanswered ask ends an automation's run after 24 hours by default, set per automation from 1 hour to 7 days or no limit.
- **D-122** After a close or crash nothing the user started resumes on its own. Home shows "N tasks stopped when Office Town closed." with Resume all and Choose (a tick-box list in the card) and a close button that holds until new work is cut off; one notice says it too. A chief goal is one row with its parts. A task paused for usage keeps its pause and stays off the card; one whose folder or account is gone shows why; continuing it by hand or deleting it cancels its waiting resume. A resume happens at most once a launch, and a task cut off while resuming in 2 launches in a row stays stopped with a reason.
- **D-124** The core decides what deserves an alert and stores it as a notice; the window shows each as an OS notification while it is not in front (M13 adds the phone). Kinds: needs you, finished, failed, a lead stopped, work stopped by a close, usage paused; each can be turned off, and one turned off makes no notice. A notice names agents, teams and tasks, never an agent's own text. The first of a kind goes out at once, more within 5 minutes once at the window's end ("2 more tasks finished"), the same kind and task once. Kept 30 days, at most 500.

## Automations

- **D-125** An automation is a saved New task (who, workspace, model, level, modes, files, app tags) plus a When: a schedule preset in an IANA zone, shortest repeat 1 hour (croner 11 computes the times; `Temporal` waits for the Node the tests run on), or after another automation, set only on the later one, loops refused and at most 5 in a row (`CHAIN_DEPTH`). Run now is an action. Every run is an ordinary task with its origin, written under its key (automation, slot) before anything starts, then through the admission queue (D-121); at start, runs still waiting go back to it with their deadline, runs cut off at work resume through it on their own, and the user's own tasks still ask (D-122). One waiting run per automation; a team never runs two of its own at once, an assistant may; per department the oldest goes first across the queue and the chief's pieces. A run shows its task's status, before that only Waiting or Skipped, with one plain reason; an automation is On, Off or Paused (three failed runs in a row, or its team, workspace or account gone), with one fix. Missed runs while closed: one catch-up run within the catch-up window, else one Skipped record with the count. Files attached are kept with it and an upload joins the workspace's Library. The last 500 runs are kept.
- **D-126** Auto (owner, 2026-11-22): a per-automation choice, for every kind of Who, that runs end to end with no Needs you decisions. The core answers in the run's place: plans and plan changes approved (a new department placed in Scratch at the Settings level), team proposals approved, questions and `propose_change` told to decide and say why in the result, stopping or moving a worker approved (D-71 waived inside an Auto run), a stopped lead stopped. Each answer reads "Decided by Auto" in the trace. Permission asks still follow the level, and Auto never means No safety checks.
- **D-127** A workspace and its Library are a live, shared place, kept safe by the core, not by a rule in the briefs (owner, 2026-11-23). Nothing is locked: when an agent changes a file another agent changed after it last read it, the core tells it at once (and the other agent, if at work), and both traces show it. Each run writes its own files (the Library result has the run in its name). A file arriving mid-run never restarts a run.
- **D-128** Events (owner, 2026-11-23): an automation can start when something arrives, from one source per automation, each a file behind one source interface (`automations/sources/`). Four now: a new file lands in any folder (edits to files already there don't count; a watched folder outside the run's workspace is linked to the run read only; a file the automation's own agents changed never starts it, one another automation's run changed counts as a step of a chain, so folders cannot loop); new posts in an RSS or Atom feed (every 15 minutes); new GitHub issues or pull requests with the GitHub app's pasted key (every 5 minutes, unchanged answers cost nothing of GitHub's limit); an agent check, a short task by whoever does the work, through its apps, every 15 minutes or more, answered with `report_found` (the checker owns `report_check`) and deleted once it answered; it follows its automation's Auto, and Usage keeps its tokens under the department's lead or the chief. Every thing seen is stored under its key before anything runs, and kept while its source still lists it, so nothing runs twice; a source's first look is a start point; what arrives while a run waits joins it, while a run works waits for it to end, at most 50 a run. Things that came while closed run within the catch-up window, else are counted on one Skipped record. What started a run reaches it as a data block (`{event}`). MCP events (SEP-3415, Beta) wait for an app that offers them, as one more source. OpenCode's own automations are parked (owner, 2026-11-24).
- **D-129** An automation can let apps act without asking (owner, 2026-11-24): Rules lists the apps with a route on Ask me first, and the ones ticked (`appsWithoutAsking`, by `appKeyOf`, so every route of an app) have their changes go through in that automation's runs, its checks and the parts of a chief goal it started. Who may use an app and Read only still decide first; reads never asked. The live automation is read at each call, so an edit or a removal applies at once. Provider-app answers read "Allowed by this automation" in the trace. Separate from Auto, which still leaves permission asks to the level (D-126). Neither the drafter nor `propose_schedule` can set it.
- **D-130** Updates: how you hear about your work outside the app (owner, 2026-11-24; replaces the first "Send results to" design and merges D-132). A place (Slack, Discord, Telegram, and under More ways email through Resend and a plain webhook; no WhatsApp) is connected once through one Connect sheet, opened from Settings, a task's options, Rules or Connectors: a short numbered guide per service (data, one file each in `features/updates/guides/`, our own theme-aware drawings, vendor steps checked 2026-11-24), one paste checked as it is made against the contract's `PASTE_PATTERNS` (the core refuses the same), and Save, which sends a test. No sign-ins, servers or vendor app registration: the pasted link or key is kept only in the credential store (D-67). Names are unique, so two of a service read apart. Places are listed and managed in Connectors under Updates. Settings > Updates says what each place hears (This computer keeps its desktop switches; a new place starts on Needs you and Fails) and the usual result places; alerts go in the core's own words only (D-124). A result goes only where asked: a person's task with Send result on (off by default, never a Settings default) sends its final text once to the result places, or a short failure note if it fails; an automation sends to its Rules' places (`rules.sendTo`, a new one starting with the result places), with its result, a failed run, a pause and a waiting ask, never traces or other files. A place an automation already speaks to is skipped for the same alert. Every place is one way: an ask says "Answer it in Office Town"; Telegram's chat is linked once by sending the bot a one-time code (10 minutes, in memory), and the core reads Telegram only while a code waits. Every message is written to an outbox under its key before it is sent (each goes out once, a restart sends what waited, a day at most); sends are spaced by each service's limit, a busy service is tried again after 1, 5 and 30 minutes, and a refusal is told on the place, the run or the task, without failing it; three in a row show on the automation, never a pause. Long results go as a file where the service takes files (Telegram, Discord), else split (Slack, 5 messages at most). Text that looks like a secret is hidden first; messages go as plain text, Slack's markup escaped, Discord's mentions off. Phone push (ntfy) and answering from afar moved to M13's phone; two-way Slack, Discord or Telegram only if the owner asks after that.
- **D-131** Nothing new (owner, 2026-11-24): the agent in charge of a run (assistant, lead or chief) gets `report_nothing_new`, only in automation runs. Such a run counts as finished well for the failures rule but sends nothing, makes no notice, skips review and the Library, keeps the last real result for `{last result}`, and fires only "however it ended" chains. Its row reads Nothing new.
- **D-133** Notes (owner, 2026-11-24): an automation keeps notes on its record, at most 8,000 characters, rewritten by the agent in charge with `keep_notes` (the core refuses more) and given to each run as a data block. Its page reads, edits and clears them; the last write wins; the drafter and `propose_schedule` never set them.
- **D-136** Ready-made teams and recipes (owner, 2026-11-25): a few hand-picked starting points beside each Describe box, never a gallery page. Picking fills the existing steps the way the drafter does and lands on Review; a code team (Code review, Bug-fix) first asks for its project folder and never falls back to Scratch, and a recipe that needs a folder opens on the step that asks for it (Nightly test check cannot be saved in Scratch). The cards hide once the user builds one manually, so a click never replaces their work. A team names only each role's power (strong or cheap), mapped on pick to what the user has: strong to the best paid provider (Opus on Claude, else its default), cheap to OpenCode's free model when it is ready, else the cheapest on the same provider; every model marked picked for you. With no provider ready the cards wait behind the existing set-up line. Recipes run on the assistant at the Settings level; one reading Gmail or Google Calendar runs on Claude Code and cannot be saved until Claude Code and that Claude app are set up. Shipped as data in the app (`features/ready-made/`), so a change is a release.

## Feed

- **D-137** Feed (owner, 2026-11-27): the office's story over time, its own sidebar item under Home with a dot for new posts (Needs you keeps its count), and one Home line "N new posts since you were here". Moments, not steps: a card per task at work that becomes its result or stop, asks, results, stops (failed, usage paused, closed), automation runs (nothing-new runs fold to one line a day), parts and milestones folded, agents' heads-ups, suggestions. An ask is the Needs you card itself, so an answer in either place closes both. A reply messages the agent in its task, as the task page's box does. Show tabs and Department as on Needs you; search; "You're caught up" where the last look ended; while scrolled, new posts wait behind a pill with up to 3 faces. Kept 7 days, results, milestones and suggestions 30, open asks and tasks at work until they close, at most about 2,000. No reactions, no mirroring to Updates.
- **D-138** Posts are a projection the core writes from what it already records (task, ask, piece and milestone changes), gathered every 250 ms into one transaction; an end or an ask counts after 3 s, so a lead's pause between turns or an ask the level answers posts nothing. A key while a post stands for one thing, plus a pass at launch (asks still waiting, tasks still at work), keeps posts single across a restart; no event checkpoint. A card's step and current action are drawn by the app from the trace it already follows, so work never writes per step. Agents post with `post_update` (asked for in every brief, as Claude defers the tool): 3 a task an hour and 30 a minute across the app; past either, the line shows on the task's card. Agent text has secrets hidden. Changes go live on the stream; a reconnect reads the newest page again.
- **D-139** Suggestions are optional and never start anything: Set it up opens New automation or New task filled in. Sources until the memory module: the same request of the user's own on 3 different days in 30 (to an automation, never twice in a month) and a lead's `follow_up` on `post_update`. At most 3 a day (turned-down ones count), none while something waits on the user; Fewer like this quiets that source for 30 days; one Settings switch turns them off. Home's "Make this a department" stays where it is.
- **D-140** The floor's own bubble carries a new heads-up, result or stop over its agent for 6 seconds, a newer post replacing it; a waiting ask's bubble still wins, a card's updates make none, and the bubble opens Feed.

## Remote

- **D-119** Recorded now so M11 and M12 do not block M13 and M14. Tailscale is the one supported path, Cloudflare Tunnel documented; the core stays on 127.0.0.1; every phone is paired and holds its own revocable key. Imported teams start at the Settings default, apps at Ask me first, automations off. Headless keys: an encrypted file, M14 only; a Mac host uses the Keychain while its user is signed in.

## Teams

- **D-40, D-42, D-55** A department is a standing team: one lead, workers, a room. Every session belongs to a stored agent. Settings flow department, role, agent; an agent may be more careful than its team, never less. A template is copied into the agent. Every agent reads, in order: About you, its team's rules, its own instructions, the task.
- **D-39, D-43** Team tools come from the core's own MCP server and return at once; outcomes reach the agent later as a message. Why: it works the same on every harness, and a tool that waits on a person hits timeouts.
- **D-44** A worker's result is its last message when its turn ends with nothing waiting and no sub-agent at work. No time limit; the user can stop it. An agent idle 10 minutes is stopped and resumed when needed.
- **D-46** A worker's worktree comes from the lead's branch, lives in the data folder, and is removed once merged.
- **D-72** The lead plans, merges and decides; workers build and report briefly with details in a file. Cost is context size times steps, so the lead's context is what to protect. Past 95% of an account's window, its tasks pause whole.
- **D-77** A failed turn gets one automatic retry, then the lead hears the real error. A lead never waits by sleeping or polling.
- **D-120** The one retry (D-77) is stored, for a delegation and for a lead (cleared when a lead turn completes), so a restart neither grants a second nor forgets one. A lead that fails after it gets a Needs you item the core answers, Try again or Stop, kept across a restart and closed by the lead's next turn by any path; the chief reads "The chief stopped after an error"; a solo agent stays Failed with Continue. A worker turn with no news for 30 minutes, no sub-agent and no ask shows so in its trace and team status, and its open lead is told once a turn; nothing stops it (D-71), and a check that runs late after sleep starts the clocks again. A result counts as delivered once the lead's session records it; one the lead never got goes first, oldest first, when the lead resumes. A message waiting on a long tool shows as waiting, and one an agent never read goes first in its next conversation (D-134).
- **D-84, D-86, D-88** A department is free once its task ends. A new task starts every agent fresh; resume never crosses tasks. Progress is honest: after 25 actions with no plan change, the step gives way to the current action.
- **D-95** Milestones (opt-in): outcomes the user sees and owns, reported by the agent. They inform and never block; a lead may send a part back at most twice, then the user decides.

## Chief

- **D-49** One standing chief. A goal goes to it only when the user chooses. Its plan is one piece per department, and the user approves it and every change. It messages leads, never workers.

## Workspaces

- **D-56** A workspace is a named list of folders: the first is where agents work, others Can edit or Read only. Scratch (a new folder per task) is only the fallback for a department with no folder. Removing a workspace never touches files.

## Usage and long runs

- **D-61** An account is one login on one harness, in its own folder handed to the CLI. Automatic picks the signed-in account with the most room. Amber from 70%, red from 90%.
- **D-94** Long chats: a handover only when the user asks, or, with Efficient on, at the next tool end past a size, before the CLI's own compaction. The new session gets the brief, the handover and the records word for word.

## Checking work

- **D-73** Finished work is checked outside the team, as an offer, never automatically. A fresh checker in a sandbox reports pass, fail or not run with evidence on a list the user approved. The user is the round limit. Why: tester and developer loop without end.
- **D-101** One task status everywhere (`taskStatus`). Finished work is To review until the user marks it Done. Every "…" menu is the shared `MoreMenu`.

## Files, Library, outputs

- **D-64** Attachments go with a message; a workspace Library gives read-only items to Everyone, departments or agents. No indexed knowledge base: search hands agents fragments, where made-up answers start.
- **D-87** An image for a model that cannot see gets a description from a cheap model, never a paid plan.
- **D-74** An output is a file or a local site. An agent's page is untrusted: it loads from a separate preview port that never sees the app's token.

## Connectors

- **D-67** The core is the hub for key apps and local programs, so every harness reaches them. Keys live only in the OS credential store. Each app's permission (Read only, Ask me first, Don't ask) decides its calls; the core, not the CLI, decides each call. The tool list never changes inside a conversation, to keep the prompt cache.
- **D-68, D-96** Provider apps (claude.ai connectors, Codex's ChatGPT apps, OpenCode's servers) are signed in to and held by their provider; the app never runs a sign-in, holds an app token or edits a provider's files, only turns apps on and off per session. Shared apps are used first. Add searches a vetted list only.
- **D-104** One status per app, the worst of its routes; Needs renewing and Not answering are the alerts.

## Interface

- **D-55, D-59, D-66** One name per thing, plain words, labels and short hints only, no explainer panels. No internal terms in what the user reads (session, harness, turn, handle, core). "Provider" for a harness; models by display name (`model-name.ts`).
- **D-35, D-48, D-52, D-62** Home is the first screen. The office floor is a view: a room per department. One side panel shape for an agent, a department and the chief.
- **D-103** One status vocabulary and one page frame: task statuses drawn only by `TaskStatusIcon`; pages use `PageHeader` and the shared widths and gaps.
- **D-38, D-58, D-80** One composer starts every task. One model picker, ordered by cost to the user. With nothing picked, OpenCode's free model runs.
- **D-79** The run card changes the model for the whole department by default, at each agent's next start.
- **D-60, D-63, D-85** Tasks are grouped by team; open work stays on top. A task's title comes from a free or cheapest model, never a paid plan.
- **D-81, D-90** Typed text is a draft that survives a restart and never brings No safety checks back without its warning. App-wide choices live on Settings; a task's own on its run card.
- **D-100 to D-109** The design audit rounds (2026-11-14): app tags, one status per screen, Providers and Usage, sidebar and Home, task page, Office and Team, the rest. Their specifics live in the code and What's new.
- **D-110** First run: two setup steps ending on a first task on the picked provider. A tutorial puts back what it replaced. Home shows one next step.
- **D-111** Settings, You and agent profiles (onboarding revamp round 2). Settings rows are label left, control right, saved at once and put back if refused, in this order: Appearance (System, Light, Dark; Interface size), Notifications (with a test), New tasks (the Permission default, stored in the core, read by solo, team, department and chief-plan starts; the composer's chip changes one task only), Accessibility, Desktop (close to tray or quit, open at login; kept by the shell), Storage and About. A Manual level the composer remembered before becomes the default once. Your profile splits how you appear from what agents read. Every agent editor (Profile, team member, template) shares one field set: Identity, Job, Runs on; Save only when changed.
- **D-112** One way to show the same thing (onboarding round 3). A department is made only through New department, and offered in one place: the empty Office's sample room. Home offers "Make this a department" only after a solo task finishes, with no department yet, drafting a team from that task. The chief is offered once a department exists. Providers are always "providers": with none ready, the composer says "No provider is ready yet." above the box, offers OpenCode's install and keeps Start off. The tutorial card sits beside its target (right, left, above, below), else in its corner.
- **D-113** Usage by provider (owner fix list, 2026-11-20). Usage is one card per provider, one row per account, its windows as columns shortest first; providers that share no limits get the same card with tokens counted here. Each provider links to its official usage page (`usagePage`). Search and Sort only past 4 accounts in a card.
