# Decisions

Grouped by topic. Code comments cite decisions as `D-n`, so every number stays in this file and is never reused: search for it. A line keeps its why only where the why still guides work. Audit after each milestone (RULES.md).

## Product and stack

- **D-1, D-2, D-4** A desktop app, since it drives CLIs on the user's machine. The core is its own local process; Electron is a thin shell around it.
- **D-3, D-12, D-19** TypeScript on Node 24 everywhere: pnpm, Zod, `node:sqlite`, Electron, React, Vite, Zustand, Biome, Vitest. No build step in development; only the installer is built (D-75).
- **D-7** Open source. Free and low-cost models are first class.
- **D-8, D-9, D-11** The app orchestrates across harnesses as a command center; a harness's own sub-agents show as nested activity. Task agnostic, with connectors as plugins (D-67).
- **D-16, D-23** Deferred: a sandbox or VM for computer use (a third `Environment`), and macOS until it can be tested on a Mac (then: `macos-latest` in CI, binaries through the login shell, signing and notarisation).
- **D-27** Withdrawn: per-agent budgets. See D-29.

## Harnesses

- **D-5, D-13, D-20** One contract, one adapter per wire format. Adapters only translate, do no I/O, and pass the same conformance tests against recordings of the real CLI. A CLI upgrade that changes its output means re-recording.
- **D-6** Run the unmodified vendor binary through its official headless mode only, and never touch its credentials: the CLI signs in and keeps its own login. No Google CLIs: their terms risk the user's account.
- **D-14, D-21, D-22** Where a harness runs (native, WSL) is an `Environment`, separate from which harness it is. Paths reach the app as host paths in `locations`; the agent's own text is never rewritten. A WSL process tree is killed through a marker set at launch.
- **D-26, D-28** A harness lists its models and efforts through a catalog query. A session resumes by the harness's own session id, only in its original environment and folder. Live text fragments are never stored.
- **D-41** Attaching our tool server and isolating the CLI. Claude: `--mcp-config`, `--allowedTools mcp__office-town`, `--setting-sources ""`, `--disable-slash-commands` (never `--bare` or `CLAUDE_CODE_SIMPLE`: they break the subscription login). OpenCode: ACP `mcpServers` with an allow rule; its global config still loads, so isolation is partial. A WSL agent reaches the core through a stdio bridge that is a Windows process; the token travels in an environment variable named in `WSLENV`, never on a command line. Worktrees are made and removed by the git of the worker's environment.
- **D-76** Harnesses: Claude Code, OpenCode (ACP), Codex (`app-server`), Muse Code (`serve`), and GitHub Copilot (`--acp`) and Cursor (`agent acp`) as launch profiles on the ACP translator. Out: Pi (no approvals), Hermes, OpenClaw. Adapters declare sign-in, version, install and account folder, so the UI never names a harness. A new harness must work end to end without breaking the others; the app never installs a CLI unasked.
- **D-77, D-83** A message reaches an agent during its turn on every harness, never mid-tool. Codex and Muse: `turn/steer`. ACP: at a tool end with nothing at work, the turn is cancelled and the message goes out at once (never a second `session/prompt`: OpenCode never answers it). Claude folds it into the turn, so the adapter emits `turn.started` from the `--replay-user-messages` echo. Conformance checks this on every harness.
- **D-92** One-off CLI queries (models, sign-in, limits, version) run two at a time; agent sessions and workers' git never wait. Why: on Windows each process start blocks the core's thread for 100 to 250 ms.

## Core: store, API, live state

- **D-15, D-30** Every event is appended to one local SQLite file behind a synchronous store interface; state and replay are read from it. WAL with `synchronous=NORMAL` (a power cut may lose the last second). One core per data folder. Every index serves a named query and the store test fails on a full scan; pages are read by key, never `OFFSET`. Large results go to files beside the database with a 4 KiB preview. Migrations are never edited once merged; the file is copied before migrating, and a file from a newer version is refused. A table comes only with the feature that uses it.
- **D-31** Store, then publish. The registry alone starts and changes sessions; reads go to the store. A shutdown records sessions as interrupted, so "stopped" means the user stopped it (or a lead, D-71). If the store fails, the agent stops: work that cannot be recorded cannot be traced.
- **D-17, D-32, D-36** Commands are HTTP; events flow on one SSE stream resuming from `Last-Event-ID` (the store's `position`). `node:http` with a route table, no framework. `127.0.0.1` only, a per-launch token on every request; errors are `{error, message}`. The UI calls its own origin (`/api`) and the shell, or Vite, forwards with the token, so the token never reaches a page showing agent text. The UI keeps one live stream (Chromium allows six connections per host). A preload is plain JS.
- **D-50** Every change to a task, agent, department, delegation, plan piece or limit is published whole after its write, as an unstored `change` frame. Task state is decided only in `team/task-state.ts`: a task has ended when its top agent owes no turn, nothing waits on the user and no work is out.
- **D-91** The core searches and counts every task (`GET /tasks/search`) with one status rule shared with the app (`contract/task-status.ts`); the app counts only live tasks. A run opens on its latest 60 blocks. Launch reads only the standing team and the agents loaded records name.
- **D-93** Provider status and models are a background job per provider, pushed as `harness` changes; `GET /harnesses/status` answers at once, `?fresh=true` waits. Change only what measurements show is slow; measure again before reopening what was left alone (CLI queries in a worker, SQLite off the main thread, caching Claude apps at launch).

## Shell and packaging

- **D-34** Closing the window keeps agents running in the tray; Quit with agents running asks and records them as interrupted. The core runs on Electron's own Node, so users install no Node, and stops when its stdin closes (tree kill after 15 s). Why stdin: Windows cannot send a child SIGTERM and a tree kill misses WSL agents.
- **D-75** electron-builder: a per-user Windows installer and a Linux AppImage, updated by electron-updater. Every green merge to `main` publishes a beta, a prerelease only the owner's app follows. A stable release happens only when the owner has tested a beta and asks; the agent never runs it. Bump `apps/desktop/package.json` after each release. Updates install on quit or Restart to update, never under a running agent, and a migration never loses data. Dev runs as "Office Town Dev" on its own data folder. Setup may run a vendor's official installer, but never a one-line PowerShell installer from a hidden process (Defender flags it), so Claude Code, Cursor and Muse keep a copy command on Windows. The app id `town.office.desktop` never changes. Signing through SignPath Foundation; betas stay unsigned.
- **D-89** The shell adds the usual text menu (spelling, copy, paste, Inspect in Dev) where the page shows none. App objects get their own menus (`ui/ActionMenu.tsx`) that only repeat existing actions. Every Stop asks first.

## Human in the loop

- **D-10, D-25, D-33** One blocked queue, Needs you, for permission requests and questions. An agent's question is its own event, not a permission.
- **D-40, D-57** Permission levels: Ask me first and Don't ask (Full), plus No safety checks (Bypass) behind More options with a warning. Outward actions (push, PR, publish) go ahead only under Full. New task, the chief and reviewers default to Full.
- **D-24, D-45** Agents run in the harness's `ask` mode; one policy in the core answers each request from its kind, paths and command, and anything it cannot read goes to the user. "Allow always" lasts one session. A session started in Bypass stays unguarded until it ends.
- **D-51, D-64** In a read-only folder only reads go through, at every level; anything else asks. The core refuses an answer it did not offer.
- **D-57** Needs you groups by task: plans and team proposals first, then questions, then approvals, oldest first. Approve all and Reject all cover approvals only, with a confirm. No undo. "Always allow this" rules are parked; the owner wants them later.
- **D-82** A task shows its level once, in a chip that saves on the department (or a solo agent) and applies at the next request; a change to or from Bypass waits for the next start.
- **D-71** An agent cutting off another needs the user's approval. A lead's `stop_work` (with a reason) waits in Needs you; `resume_work` does not. A stop ends the delegation, interrupts the turn, then closes the process, since Claude's sub-agents would keep spending.
- **D-78** A lead that would change direction (drop what the goal names, deliver something else, or less) asks first with `propose_change`, a question at every level. If leads skip it in practice, the next step is a cheap watcher.

## Teams

- **D-40, D-42, D-55** A department is a saved standing team: one lead, workers, a room. Every session belongs to a stored agent (handle, colour, role, department). Settings flow department, role, agent; an agent may be more careful than its team, never less. A template is copied into the agent (`profileId` only counts uses). Every agent reads, in order: About you, its team's rules, its own notes, the task (`agents/briefs.ts`).
- **D-39, D-43** Team tools come from the core's own MCP server, one token per agent session, offered to a lead from its first session (a harness reads its tool list once). Tools return at once; outcomes reach the agent later as a message. Why: it works the same on every harness, and a tool that waits on a person hits harness timeouts. Trace titles for our tools come from one rule (`trace/team-tools.ts`).
- **D-44, D-83** A worker's result is its last message when a turn ends with nothing waiting; it reaches the lead as a message. A brief to a busy worker is queued (`registry.tell`) and folds into its piece. An agent idle 10 minutes is stopped and resumed when needed.
- **D-46** A worker's worktree comes from the lead's branch (one branch per worker is a department switch, on by default), lives in the data folder, and is removed once merged; the branch stays.
- **D-72** The lead manages: it plans, writes shared contracts, merges and decides; workers build and report in under 200 words with details in a file; command output stays quiet. Cost is context size times steps, so the lead's context is what to protect. Results are not batched, models stay the user's choice, no budgets.
- **D-77** A failed turn or process gets one automatic retry, then the lead hears the real error. A process that dies between turns once its work is done (nothing owed, nothing asked, no part at work) ends as an idle stop, not failed; its error stays in the trace. A lead never waits by sleeping or polling. `change_worker` moves a worker to another model of its provider, following the department's level.
- **D-84, D-86, D-88** A department is free once its task ends; only an open check holds it. A new task starts every agent in a fresh conversation, and resume never crosses tasks. Every message to a lead continues the team (`continueTeam`), which closes cut-off work.
- **D-65** Teams are built from a description (a stateless draft run that returns JSON and stores nothing) or step by step. A removed department keeps its row so history keeps its name.
- **D-95** Milestones, opt-in like Efficient. A goal and each part carry milestones the user sees and owns: one outcome and how the user will see it, in plain words, at least one, no cap (a nudge past 12). The lead or solo agent writes the goal's first with `set_milestones`, a lead gives each part its own on `delegate`, and the chief's ride on `propose_plan` pieces, becoming the department's goal milestones when the piece starts (the same rows). The owner reports each with `report_milestone`. They inform and never block: a task ends as before (D-50). A part with every milestone met is done at once, with a notice nothing waits on; `send_back` sends a worker only the failing items, at most twice per part, kept by the core, then the user decides in Needs you. The user edits milestones and asks for steps at any time: stored at once, told to the owner at its next tool end, shown as taken at its next turn. The tools reach an agent at its next start, as an AI app reads its tools once (owner). With it on, the checker starts from the goal's milestones and a handover's progress and steps come from the record. Off, briefs read as before and no milestone tool is offered. One Progress view replaces Steps.
- **D-69** A department has several workspaces, the first its default; each goal runs in one, and a change applies from the next goal.

## Chief

- **D-49, D-51** One standing chief. A goal goes to it only when the user chooses, one at a time. Its plan is a graph of pieces, one per department, and the user approves it and every change. It messages leads, never workers. A piece runs as its department's own task once its inputs are done and the department is free; downstream gets the upstream result and read-only access to its folder. A user's message to a worker is noted to its lead while the lead works.

## Workspaces

- **D-33, D-56, D-79, D-82** A workspace is a named, ordered list of folders: the first is where agents work, extra folders are Can edit or Read only. Scratch makes one folder per task, `YYYY-MM-DD HH-MM <8 hex>`, under `~/OfficeTown/Scratch`, and is only the fallback for a department with no folder. Workers work where their lead does. A session keeps its folders; a resume whose folder is gone is refused. Removing a workspace never touches files.

## Usage and long runs

- **D-29, D-76** Each provider's own usage limit is the truth; no budgets or dollar tracking. Without a limit, tokens with cached input apart; where a provider shares no plan usage (Copilot, Cursor), an estimate at API prices from models.dev, labelled as such.
- **D-61** An account is one login on one harness; an added one lives in its own folder handed to the CLI (`CLAUDE_CONFIG_DIR`, `XDG_DATA_HOME`, `CODEX_HOME`, `COPILOT_HOME`, `CURSOR_CONFIG_DIR`). Automatic picks the signed-in account with the most room. Limits come from runs and on demand (Claude's `/api/oauth/usage` with the CLI's token, never refreshed by us). Amber from 70%, red from 90%.
- **D-70** OpenCode undercounts tokens, so a session is recounted once it ends; `usage.recounted` carries only the missing part, so sums just add it.
- **D-72** Past 95% of an account's window, every task on it pauses whole, to resume at the reset or now.
- **D-94** Long chats. One place (default): a handover only when the user asks or accepts the one suggestion past 300k. Efficient (opt-in: app default in Settings, per task on the run card and the composer's Options): every role except a checker is asked at its next tool end past 350k or 80% of its window, before the CLI's own compaction. The agent writes its handover while its cache is warm; the new session gets its brief, the handover, the records word for word and the earlier conversation as a file to search. No one else spends a turn: messages are held and an open delegation moves in place. Handovers are files under `handovers/`, shown in Outputs. Open: Claude's idle compaction was not probed; a held message is lost if the session crashes mid-switch.

## Checking work

- **D-18, D-47, D-54, D-73** Finished work is checked outside the team, as an offer, never automatically. The lead or solo agent writes the checklist (`write_checklist`). Send for review starts a fresh checker with full context in a sandbox (a detached worktree, else a copy without `.git` and `node_modules`), removed when it ends. It proposes at most 10 items; the user edits and approves the list, which then freezes. It reports pass, fail or not run with evidence. The user is the round limit: Send fixes (failing items only), Check again (the whole list), Accept as is. Inside the team each piece is checked once, with no end-to-end rounds; with Milestones on, a lead may send a part back at most twice (D-95). Why: tester and developer loop without end, and gains flatten after 2 to 3 rounds.

## Files, Library, outputs

- **D-64** Attachments go with a message; a workspace Library gives reference items to Everyone, departments or agents. Files are copied read-only with a checksum; folders are linked live, read-only. Each item reaches the agent as read-only access plus a list in its prompt; images also inline when the model sees them. Opened or Not opened comes from the agent's own reads. Agents add to the Library freely; replacing or removing asks. 20 MB per file, 5 MB per inline image. No indexed knowledge base: search hands agents fragments, where made-up answers start.
- **D-87** An image for a model that cannot see images gets a written description from a cheap model that can (never a paid plan), sent beside it as a file. The message waits up to 90 s, else the path goes alone.
- **D-74** An output is a file or a local site, marked with `show_result`. An agent's page is untrusted: it loads from a separate loopback preview port that serves only granted folders and never sees the app's token. Versions are kept (copies up to 10 MB). Nothing loads until opened, one preview at a time.

## Connectors

- **D-67** The core is the hub: one live link per key app or local program, re-served on the tool server so every harness reaches it. Keys live only in the OS credential store (Windows refuses to save otherwise). Who may use it follows the Library's audience. Each connector's permission (Read only, Ask me first, Don't ask) decides its own calls whatever the department's level; reads never ask. The tool list never changes inside a conversation, to keep the prompt cache: apps granted later go through the fixed hub tools `list_app_tools` and `use_app_tool`. The core, not the CLI, decides each call. Describe-it finds existing servers only.
- **D-68** Sign-in apps are the user's claude.ai connectors, for Claude agents only; the app holds no app token. They are read with `mcp_status`, fixed per conversation, and the rest are denied (`deniedMcpServers`; `--strict-mcp-config` is not used). Each call asks, and the core answers by the app's permission. Under Bypass they run unguarded (owner accepted).

## Interface

- **D-37, D-53** React 19, Vite, Zustand, Radix, CSS Modules with one tokens file (no Tailwind), `react-markdown` (never raw HTML). Look "Dusk": warm greys, slate blue for actions, amber only for what needs the user, status as small icons, Plus Jakarta Sans at 14 px, theme follows the OS, reduced motion respected.
- **D-55, D-59, D-66** Words: one name per thing, plain and human, labels and short hints only, no explainer panels. No internal terms in what the user reads (session, harness, turn, handle, core, trace); "Provider" for a harness; Allow or Deny for permission requests, Approve for plans and teams; models by display name (`features/profiles/model-name.ts` is the only namer). Onboarding may explain in one short sentence.
- **D-35, D-48, D-52, D-62** Home is the first screen. The office floor is a view: a room per department, desks lead first. One side panel shape for an agent, a department and the chief.
- **D-38, D-58, D-80** One composer starts every task, with remembered chips. One model picker (`ModelChip`, two panes), ordered by cost to the user; models that cannot call tools are left out. It never waits on the CLIs at launch: the last known lists show first. With nothing picked, OpenCode runs DeepSeek V4.1 Flash Free at max thinking.
- **D-79** The run card changes provider, model and thinking for the whole department by default, taken at each agent's next start; a move to another provider starts a new conversation with a handover.
- **D-60, D-63, D-85** Tasks are grouped by team with search and filters. A task's title comes from a short run on a free or cheapest model, never a paid plan.
- **D-81, D-90** Typed text is a draft (`useDraft`): it survives a restart, expires after 30 days, and never brings Bypass back without its warning. Where the user was (filters, folds, scroll) is kept for the session (`store/kept.ts`); preferences are saved through `api/last-known.ts`. App-wide choices live on Settings, above Help; a task's own are switches on its run card.
- **D-83, D-84, D-88** Progress is honest: after 25 actions with no plan change, the step gives way to the current action. A turn names its stage (Starting, Waiting for the model, Thinking). An agent's chat is one stream with a folding header per task.
